# Mini-RPC 批次执行计划

## 结论

v0.1.0 按功能闭环和验收依赖拆为 **13 个批次**，对应技术设计中的阶段 0 至阶段 12。当前所有批次均已完成，阶段 12 包含最终压测、工程化、发布验收和 v0.1.0 固定。

如果采用“一个写入批次 + 一个独立审查批次”的流程，则执行动作是 26 次，但交付里程碑仍然是 13 个批次。面试材料、简历描述和可选扩展不属于 v0.1.0 的必选批次。

## 可并行边界

默认串行执行最安全。若需要并行，可在完成阶段 4 后让以下工作共享稳定接口并行推进：

- 连接池（阶段 4）与注册中心（阶段 5）可以由不同执行者开发，但需要先冻结传输接口。
- 负载均衡（阶段 6）可以与超时取消（阶段 7）并行，但负载均衡必须基于已完成并测试的实例快照接口。
- 限流（阶段 9）的纯令牌桶实现可以先于熔断集成开发，但调用链接线必须在阶段 8 后完成。

不应并行修改协议帧、pending map、连接生命周期和治理调用链。这些是其他模块的共同依赖，返工会扩散到多个批次。

## 每批执行门槛

1. 检查当前分支、最近提交和前置批次报告。
2. 只实现本批范围；新增公共接口时先补接口测试和文档。
3. 运行本阶段测试标准，并至少执行 `go test -race` 覆盖并发模块。
4. 更新 README、协议或专题文档。
5. 审查 diff，确认没有调试输出、临时依赖和越界修改。
6. 创建独立语义提交，并在 `docs/reports/` 写入阶段报告。

## 最终完成定义

只有同时满足以下条件，v0.1.0 才算完成：

- 生成的客户端和服务端代码可以完成真实 RPC 调用。
- 多实例服务可以注册、发现、负载均衡并在实例下线后恢复。
- 超时、取消、重试、熔断和限流行为符合配置且无无限循环。
- 协议、连接关闭、Watch、连接池和 pending map 的相关测试通过竞态检测。
- Prometheus 指标、Trace 和结构化日志可以关联客户端与服务端调用。
- Docker Compose 可以一键启动完整发现示例；故障场景可由 `make fault-test` 确定性执行。
- benchmark 报告包含环境、消息大小、并发、QPS、P50/P95/P99、资源占用、错误率和提交 SHA。
- 所有阶段均有独立提交、测试结果、已知限制和下一阶段依赖记录。
